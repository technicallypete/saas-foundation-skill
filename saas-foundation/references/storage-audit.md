# Object storage and audit

## ObjectStore boundary

- Domain code depends on an owned `ObjectStore` interface (`Put`, `Get`, `Delete`, `SignedGetURL`, `Metadata`); provider adapters sit behind it. The skeleton and fixtures use `aws-sdk-go-v2` with path-style addressing, which works against MinIO locally and S3-compatible production stores.
- PostgreSQL holds object metadata (`stored_objects`: id, `organization_id`, optional Group scope, opaque key, content type, creator); the object store holds bytes.
- **Authorization before access:** a signed URL is issued only when (1) the metadata row is visible to the caller under row-level security with the caller's tenant context and (2) the caller holds the read capability of the object's owning scope. A foreign object behaves exactly like a nonexistent one.
- **Prefixes confer nothing.** Keys are server-generated and opaque; client-supplied keys, traversal and encoded separators are rejected; a guessed key under one's own prefix without a metadata row is denied.
- **Signed URLs** use a capped TTL (the revocation exposure window) and are audited when issued.
- **Credentials** are scoped and resolved on the server: the application uses a non-root credential limited to its bucket (`infra/minio/init.sh` creates it); root credentials stay with the storage service and its init job. Buckets are private (anonymous access denied).
- **Local MinIO** is built from the final upstream community source release because upstream no longer publishes maintained images; it is archived and unmaintained, for local development and validation only. Production uses the configured S3-compatible provider (STAGE-STORAGE).

## AuditEvent

| Field | Notes |
|---|---|
| `id` | Generated by the writer (no `RETURNING` needed) |
| `occurred_at` | Server time; the runtime role cannot set it (column-level INSERT grant) |
| `actor_type`, `actor_id` | `user`, `service` or `system` |
| `organization_id` | Required, except for security events that happen before any context exists |
| `group_id` | Optional |
| `resource_type`, `resource_id` | What was acted on |
| `action`, `outcome` | `allowed`, `denied` or `error` |
| `trace_id`, `request_id` | Correlation with logs and traces |
| `detail` | Non-sensitive structured context only; never secrets or tenant content |

Record at least: security denials, context changes, membership and role changes, administrative mutations, signed-URL issuance. Write the event **in the same transaction** as the mutation.

## Controls (an append-only API alone is insufficient)

1. Privileges: the runtime role has `INSERT` only on `audit_events`; no `SELECT`, `UPDATE`, `DELETE` or `TRUNCATE`.
2. Row-level security pins inserted events to the active Organization.
3. A trigger refuses `UPDATE`, `DELETE` and `TRUNCATE` for every role, including the owner path, except `DELETE` by the retention role of rows older than the retention window.
4. The retention role can read only `id` and `occurred_at` and sees only expired rows.
5. Residual risk: the table owner can disable triggers during migrations; keep migrations reviewed and consider hash chaining at STAGE-AUDIT.
